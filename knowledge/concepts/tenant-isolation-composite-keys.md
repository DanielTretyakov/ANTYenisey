# Tenant Isolation via Composite Foreign Keys

Стратегия изоляции клубов (tenant'ов) в платформе [[concepts/yenisey-platform-overview]]. Поле `tenantId` дублируется во все дочерние таблицы, а внешние ключи строятся по паре `(id, tenantId)`. Postgres Row-Level Security (RLS) отклонён как избыточный на текущем этапе.

## Key Points

- **Составные внешние ключи**: связи между таблицами идут по паре `(id, tenantId)`, а не по одному `id`. Postgres физически не принимает запись, связывающую сущности разных клубов.
- **tenantId в каждой дочерней таблице**: поле продублировано даже там, где оно может быть выведено через JOIN — сознательный trade-off для обеспечения изоляции на уровне СУБД.
- **RLS отклонён**: Row-Level Security признан избыточным — составные FK дают достаточную гарантию без дополнительной сложности в администрировании.
- **Prisma поддерживает**: Prisma 6.x допускает участие одной колонки (`tenantId`) сразу в нескольких составных связях — проверено валидатором, хотя не очевидно из документации.

## Details

Решение продублировать `tenantId` во все дочерние таблицы выглядит денормализацией, но преследует конкретную цель: сделать кросс-тенантные ссылки невозможными на уровне базы данных, а не полагаться на проверки в коде приложения. Два параллельных запроса к API не смогут создать бронирование, в котором сессия принадлежит одному клубу, а клиент — другому, потому что FK-констрейнт по `(id, tenantId)` это физически запрещает.

Альтернативой был Postgres RLS — механизм, при котором база фильтрует строки по `current_setting('app.tenant_id')`. RLS отклонён по двум причинам: (1) добавляет сложность в настройку подключений и миграций, (2) не даёт преимуществ перед составными FK при текущей архитектуре, где все запросы проходят через ORM с обязательным `tenantId` в `WHERE`. RLS может быть добавлен позже как дополнительный слой защиты, если появятся прямые SQL-запросы в обход ORM.
