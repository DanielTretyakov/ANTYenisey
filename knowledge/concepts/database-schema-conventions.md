# Database Schema Conventions

Набор конвенций и архитектурных решений, принятых при проектировании схемы БД платформы [[concepts/yenisey-platform-overview]]. Схема утверждена: 28 таблиц, Prisma 6.x, проверена на живом PostgreSQL с тестами на ограничения целостности.

## Key Points

- **28 таблиц**: 18 следуют напрямую из ТЗ, 10 добавлены при ревью схемы (вспомогательные: тарифы, ступени отмены, журналы и т.п.). Предложение сократить или разбить на волны отклонено.
- **Деньги — в копейках (Int)**: все денежные суммы хранятся как целые числа в копейках, не в рублях с дробной частью. Конвертация в рубли — на границе слоя представления.
- **Мягкое удаление**: удаление клиента — `deactivatedAt`/`anonymizedAt`, не физический `DELETE`. На всех FK — `onDelete: Restrict`.
- **Raw SQL для сложных констрейнтов**: exclusion-констрейнты (пересечение временных слотов), частичные уникальные индексы и CHECK-ограничения выносятся в raw-SQL миграцию, т.к. Prisma их не поддерживает.
- **Prisma 6.x**: схема валидна на Prisma 6.x; на Prisma 7 падает из-за изменения конфигурации datasource (`url` переехал в `prisma.config.ts`).

## Details

Решение хранить деньги в копейках (а не в Decimal или Float) — стандартная практика для финансовых приложений: исключает ошибки округления при арифметике с плавающей точкой и упрощает сравнения. Все суммы в API и UI конвертируются из/в рубли на границе слоя представления.

Запрет физического удаления (`onDelete: Restrict` на всех внешних ключах) обусловлен тем, что данные клуба содержат финансовые транзакции и персональные данные: удаление записи может нарушить целостность отчётности или создать «висячие» ссылки. «Удаление» клиента реализуется через поля `deactivatedAt` (мягкое удаление) и `anonymizedAt` (обезличивание персданных по GDPR/ФЗ-152).

Ограничения, которые Prisma не умеет выражать декларативно (exclusion constraints для предотвращения пересечения временных слотов на одном столе, частичные уникальные индексы), реализуются через `prisma migrate` с кастомным SQL. Проверка таких ограничений только в коде приложения недостаточна: два параллельных запроса могут увидеть стол свободным и создать пересекающиеся брони. Только СУБД-уровень гарантирует атомарность.

При тестировании констрейнтов обнаружен антипаттерн: блок `EXCEPTION WHEN others` в PL/pgSQL засчитывает любую ошибку как «прошёл», включая ошибки не по целевой причине. Корректный подход — проверять код ошибки и имя ограничения через `GET STACKED DIAGNOSTICS`.
