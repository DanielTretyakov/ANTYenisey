# Локальная разработка

Монорепозиторий «Енисея»: Next.js (веб), NestJS (API), Prisma (схема БД),
Turborepo как оркестратор задач.

## Что нужно на машине

| Инструмент | Версия | Замечание |
|---|---|---|
| Node.js | ≥ 22 (проверено на 24.11) | тесты используют нативное срезание типов TS |
| pnpm | **строго 10.x** | см. «Почему pnpm 10» |
| PostgreSQL | 18 | ставится нативно, Docker для разработки не нужен |

## Структура

```
apps/
  api/                 NestJS: REST API, авторизация, бизнес-логика
  web/                 Next.js: клиентский интерфейс и личный кабинет
packages/
  database/            Prisma-схема, миграции, сгенерированный клиент, сид
  types/               общий контракт HTTP между api и web
docs/
  TZ.md                техническое задание
  DEVELOPMENT.md       этот файл
  DESIGN.md            дизайн-система: токены, темы, шрифты, логотип
```

Пакеты workspace отдают приложениям **готовый CommonJS**, а не
TypeScript-исходники, и это не формальность: Node в рантайме требует от
`.ts`-модулей явных расширений в импортах и спотыкается на пути каталога.

- `@yenisey/types` собирается в `dist/` (`tsc`), поэтому `dev` и `build`
  зависят от сборки пакетов — turbo выстраивает порядок сам;
- `@yenisey/database` ничего не собирает: его точка входа ведёт прямо в
  клиент, сгенерированный Prisma. Барреля-обёртки нет намеренно.

## Первый запуск

```bash
pnpm install

cp .env.example .env
# Подставить в .env пароль от Postgres и два РАЗНЫХ секрета:
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

# Две базы: рабочая и теневая (последняя нужна prisma migrate dev)
createdb -U postgres -h 127.0.0.1 yenisey_dev
createdb -U postgres -h 127.0.0.1 yenisey_shadow

pnpm db:generate                             # сгенерировать Prisma-клиент
pnpm --filter @yenisey/database migrate      # накатить миграции
pnpm --filter @yenisey/database seed         # завести клуб «Енисей» с ценами из ТЗ

# Сотрудники клуба. Отдельной командой, а не сидом: сид лежит в репозитории,
# и пароль из него попал бы в git вместе с историей.
pnpm db:create-admin -- --email admin@club.ru --password "..."   --name "Иванов Иван Иванович" --phone +79991234567 --birthdate 1985-03-12
pnpm db:create-admin -- --email coach@club.ru --password "..." --role COACH   --name "Петров Пётр Петрович" --phone +79997654321 --birthdate 1990-07-04

pnpm dev                                     # api :3001, web :3000
```

В строке подключения — именно `127.0.0.1`, а не `localhost`: последний
резолвится в `::1`, а IPv6-порт Postgres на этой машине закрыт
брандмауэром, и подключение отваливается по таймауту.

После сида доступен клуб с кодом `yenisey` — он подставлен в формы входа и
регистрации по умолчанию.

## Ежедневные команды

```bash
pnpm dev                                     # оба приложения в watch-режиме
pnpm build                                   # сборка всего
pnpm typecheck                               # проверка типов по всем пакетам
pnpm test                                    # тесты
pnpm db:studio                               # веб-интерфейс к базе

pnpm --filter @yenisey/database verify        # прогон схемы на одноразовой базе
```

Проверить работающий API целиком, включая guard'ы и живой Postgres:

```bash
pnpm smoke              # 160 сценариев против поднятого API
pnpm db:clean-probes    # убрать заведённых им probe-*@example.com
```

Раздел про профиль клуба закрыт ролями, поэтому ему нужна учётка
администратора — без неё эти сценарии честно пропускаются с пояснением:

```bash
SMOKE_ADMIN_EMAIL=admin@club.ru SMOKE_ADMIN_PASSWORD="..." pnpm smoke
```

Проверяются: регистрация и склейка ФИО, занятый email, чужой клуб, попытка
выдать себе роль владельца лишним полем, правила для ФИО и телефона, доступ
к защищённому маршруту без токена и с подделанным, вход, ротация
refresh-токена, обнаружение повторного использования, выход, публичное
название клуба и валидация формы. Отдельно — оба транспорта refresh-токена
(httpOnly-кука для браузера и тело ответа для мобильного клиента),
остановка подбора пароля, профиль клуба (залы со своими ценами, столы,
расписание — шаблон недели и правки на даты, тренер у занятия и клиент у
аренды) и состав клуба с поиском и постраничной выдачей.

`verify` разворачивает схему с нуля, накатывает ограничения целостности и
выполняет сценарии, которые проверяют, что база физически не даёт смешать
данные двух клубов. Направлять его можно **только** на пустую одноразовую
базу — он пишет туда заведомо некорректные данные.

## Переменные окружения

Все переменные валидируются при старте API (`apps/api/src/config/env.ts`) —
приложение падает сразу с внятным сообщением, а не через неделю на проде.
Отдельно проверяется, что `JWT_ACCESS_SECRET` и `JWT_REFRESH_SECRET`
различаются: при совпадении refresh-токен принимается как access и обходит
короткий срок жизни.

`.env` лежит в корне монорепозитория в единственном экземпляре и в git не
попадает; в репозитории только `.env.example`.

## Почему pnpm 10, а не 11

На pnpm 11 установка пакетов с нативными бинарниками (`argon2`, `esbuild`,
`node-gyp-build`) падает с `ERR_PNPM_EPERM`: целевой каталог успевает
создаться пустым, а Windows не позволяет переименовать каталог поверх
существующего — даже пустого. Это гонка, зависящая от скорости тома: на
диске X воспроизводится стабильно, на C — нет. Версия закреплена в
`packageManager`; поднимать её до 11 без проверки не нужно.

Там же, в `package.json`, поле `pnpm.onlyBuiltDependencies`: pnpm 10 по
умолчанию не выполняет postinstall-скрипты зависимостей, а Prisma, argon2 и
sharp без них нерабочие.

## Миграции

Ограничения целостности, невыразимые в Prisma (exclusion-констрейнт на
пересечение броней стола, частичные уникальные индексы, check'и), лежат в
`packages/database/prisma/constraints.sql` и накатываются отдельной
миграцией `*_integrity_constraints`. При изменении этого файла нужно
завести **новую** миграцию, а не править применённую: Prisma сверяет
контрольные суммы и откажется работать с изменённой задним числом.

## Что уже реализовано

Сквозной сценарий авторизации: регистрация клиента → вход → защищённый
маршрут `/api/auth/me` → обновление пары токенов → выход.

**Профиль клуба** — раздел `/club`, доступный ролям `admin`/`owner`: название
и часовой пояс, минимальный шаг брони, цены аренды стола и отдельная сетка
цен «стол + робот», правила присутствия и неявки, список столов с
добавлением, переименованием и удалением. Стол с бронями удалить нельзя — за
бронями стоят платежи, и внешний ключ стоит на `Restrict`.

**Расписание зала** — там же, сеткой «время × столы» с 06:00 до полуночи.
Два режима: **шаблон недели** (`TableClosureRule`) описывает, как зал живёт
обычно, **расписание даты** (`HallDaySchedule` + `DayClosure`) правит
конкретный день и ЗАМЕНЯЕТ шаблон на эту дату целиком — иначе убрать одно
занятие в одну субботу было бы нечем. Пустое расписание правленого дня —
законное состояние, и заголовок `HallDaySchedule` нужен именно чтобы
отличить его от «день не трогали».

**Занятия и турниры** — раздел `/catalog`: типы тренировок («Общая
групповая», «Первая подача») с ценой и типы турниров со справочным
ограничением по рейтингу. Сам турнир там не заводится: его создаёт
постановка в сетку расписания — выбираете кисть «Турнир» и его тип,
закрашиваете время, и турнир появляется в списке уже с датой. Дата и время
начала берутся из сетки, вводить их дважды незачем.

Назначения «другое» в палитре нет: оно ничего не объясняло ни администратору
через месяц, ни статистике. В enum значение остаётся — на него ссылаются уже
заведённые окна. Снятые с продажи
записи не удаляются, а гасятся: на них ссылается расписание, и удаление
упёрлось бы во внешний ключ.

У каждого окна есть назначение (аренда, спарринг, тренировка, робот, турнир,
другое) и закреплённый человек: у тренировки и спарринга — **тренер**, у аренды и
робота — **клиент**. У тренировки обязательны и тренер, и тип занятия: без
тренера оно не попадёт в его статистику, без типа клиенту непонятно, на что
он записывается, и неоткуда взять цену. Турнир возможен только в расписании
конкретной даты — у него дата и время, и в постоянном шаблоне недели ему
места нет; перекрёстные поля запрещены, а не просто необязательны —
тренер у аренды набрал бы чужие часы, а «закреплённый клиент» у тренировки,
где участников десяток, ввёл бы в заблуждение. Проверка стоит и в API, и
CHECK-констрейнтом в базе.

В сетке **цвет клетки — это человек**, а не назначение: тренеров и
арендаторов в расписании десятки, и различать их по подписи тяжело, а
назначений всего пять. Назначение обозначено буквой в углу клетки (А, С, Т,
Р) — буква читается на любом цвете, в отличие от второго цвета рядом.

**Состав клуба** — отдельный раздел `/people`, а не вкладка в настройках:
настройки правят изредка и осознанно, а список людей открывают по нескольку
раз в день, чтобы кого-то найти. Сотрудники и клиенты одним списком с
поиском по ФИО, почте и телефону; отключённые не пропадают, а помечаются.

Закрыто **только для клиента**: администратор посадить человека за такой
стол по-прежнему сможет. Функция, которая это проверяет, уже написана и
покрыта тестами (`apps/api/src/club/closures.ts`), но звать её пока некому —
движка бронирования нет, и до его появления расписание ни на что не влияет.

Дальше этого (записи, оплаты, турниры) пока не реализовано ничего.

Формы:

- ФИО спрашивается **тремя обязательными полями** и склеивается в
  `User.fullName` на сервере. В одно поле «ФИО» люди вписывают что
  придётся («Иван», «Иванов И.»), и администратор потом не может ни найти
  человека, ни обратиться к нему по имени;
- телефон вводится с **несъёмным «+7»**: префикс нарисован рядом с полем, а
  не лежит в его значении, поэтому стереть его нельзя. Вставка номера в
  любом виде («8-999-…», «+7 (999) …») превращается в десять цифр;
- **код клуба не вводится и не показывается.** Человек видит официальное
  название («АНТ «Енисей»»), полученное из открытого `GET /api/tenants/:slug`;
  код уходит в запрос сам и случайной правке не подлежит.

- пароли — argon2id (19 МиБ памяти, 2 прохода);
- access-токен JWT на 15 минут, refresh — 256 случайных бит на 30 дней,
  в базе только SHA-256 от него;
- **refresh-токен уезжает браузеру в httpOnly-куке**, а не в теле ответа:
  `SameSite=Lax`, путь сужен до `/api/auth`, `Secure` в production. В теле
  токен остаётся только по явному заголовку `X-Auth-Transport: body` — так
  его будет забирать мобильное приложение, у которого кук нет. Access-токен
  на клиенте живёт **только в памяти вкладки**: после перезагрузки страницы
  сессия восстанавливается обменом куки;
- **подбор пароля останавливается** после 10 неудачных попыток подряд по
  одной учётке (`AUTH_MAX_FAILED_ATTEMPTS`, окно `AUTH_ATTEMPT_WINDOW`).
  Считаются только провалы, ключ — «клуб + почта», удачный вход обнуляет
  счётчик. Плюс грубый лимит `RATE_LIMIT` на весь API против заваливания
  запросами;
- ротация refresh-токена при каждом обновлении, с обнаружением повторного
  использования: предъявленный дважды токен гасит все сессии пользователя;
- `JwtAuthGuard` подключён **глобально** — по умолчанию закрыт каждый
  маршрут, открытые помечаются `@Public()`.

## Известные ограничения каркаса

- **Счётчик неудачных попыток входа живёт в памяти процесса.** Для одного
  экземпляра API этого достаточно; когда экземпляров станет несколько, окно
  придётся перенести в общее хранилище (Redis), иначе лимит умножится на
  число процессов.
- **Логотип отрисован вручную.** Знак в `LogoMark` набран по растровым
  файлам брендбука, оригинального вектора в репозитории нет. Там же на глаз
  снят изумруд `--brand-600`. Подробнее — `docs/DESIGN.md`.
- **Телефон и дата рождения обязательны у всех ролей.** У сотрудников,
  заведённых до этого правила, их неоткуда взять, и миграция подставила
  заметные заглушки — `+70000000000` и `01.01.1900`. Их видно в составе клуба
  с первого взгляда, и администратор должен их заменить.
- **Тренерам, администраторам и владельцу ФИО проставлено плейсхолдером.**
  Миграция `20260826060000_user_full_name` перенесла имена клиентов из
  `ClientProfile`, но у остальных ролей их раньше просто не хранили — там
  стоит «Имя не указано». Проставить настоящие сможет администратор клуба,
  когда появится экран управления сотрудниками.
- **Отчество обязательно.** У иностранцев и части народов России его нет в
  паспорте. Требование введено осознанно — чтобы люди не игнорировали поле,
  — но при появлении таких клиентов его придётся ослабить.
- **Код клуба берётся из `NEXT_PUBLIC_TENANT_SLUG`**, то есть один экземпляр
  веб-приложения обслуживает один клуб. Когда клубов станет несколько, код
  должен приходить из адреса (поддомен или сегмент пути).
