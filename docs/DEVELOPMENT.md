# Локальная разработка

Монорепозиторий «Енисея»: Next.js (веб), NestJS (API), Prisma (схема БД),
Turborepo как оркестратор задач.

## Что нужно на машине

| Инструмент | Версия | Замечание |
|---|---|---|
| Node.js | ≥ 22 (проверено на 24.11) | тесты используют нативное срезание типов TS |
| pnpm | **строго 10.x** | см. «Почему pnpm 10» |
| PostgreSQL | 18 | ставится нативно, Docker для разработки не нужен |

## Структура

```
apps/
  api/                 NestJS: REST API, авторизация, бизнес-логика
  web/                 Next.js: клиентский интерфейс и личный кабинет
packages/
  database/            Prisma-схема, миграции, сгенерированный клиент, сид
  types/               общий контракт HTTP между api и web
docs/
  TZ.md                техническое задание
  DEVELOPMENT.md       этот файл
  DESIGN.md            дизайн-система: токены, темы, шрифты, логотип
```

Пакеты workspace отдают приложениям **готовый CommonJS**, а не
TypeScript-исходники, и это не формальность: Node в рантайме требует от
`.ts`-модулей явных расширений в импортах и спотыкается на пути каталога.

- `@yenisey/types` собирается в `dist/` (`tsc`), поэтому `dev` и `build`
  зависят от сборки пакетов — turbo выстраивает порядок сам;
- `@yenisey/database` ничего не собирает: его точка входа ведёт прямо в
  клиент, сгенерированный Prisma. Барреля-обёртки нет намеренно.

## Первый запуск

```bash
pnpm install

cp .env.example .env
# Подставить в .env пароль от Postgres и два РАЗНЫХ секрета:
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

# Две базы: рабочая и теневая (последняя нужна prisma migrate dev)
createdb -U postgres -h 127.0.0.1 yenisey_dev
createdb -U postgres -h 127.0.0.1 yenisey_shadow

pnpm db:generate                             # сгенерировать Prisma-клиент
pnpm --filter @yenisey/database migrate      # накатить миграции
pnpm --filter @yenisey/database seed         # завести клуб «Енисей» с ценами из ТЗ
pnpm db:seed-demo                            # ближайшие занятия и турниры, чтобы страница клуба была непустой

# Сотрудники клуба. Отдельной командой, а не сидом: сид лежит в репозитории,
# и пароль из него попал бы в git вместе с историей.
pnpm db:create-admin -- --email admin@club.ru --password "..."   --name "Иванов Иван Иванович" --phone +79991234567 --birthdate 1985-03-12
pnpm db:create-admin -- --email coach@club.ru --password "..." --role COACH   --name "Петров Пётр Петрович" --phone +79997654321 --birthdate 1990-07-04

pnpm dev                                     # api :3001, web :3000
```

В строке подключения — именно `127.0.0.1`, а не `localhost`: последний
резолвится в `::1`, а IPv6-порт Postgres на этой машине закрыт
брандмауэром, и подключение отваливается по таймауту.

После сида доступен клуб с кодом `yenisey` — он подставлен в формы входа и
регистрации по умолчанию.

## Ежедневные команды

```bash
pnpm dev                                     # оба приложения в watch-режиме
pnpm build                                   # сборка всего — НЕ на работающем pnpm dev
pnpm typecheck                               # проверка типов по всем пакетам
pnpm test                                    # тесты
pnpm db:studio                               # веб-интерфейс к базе

pnpm --filter @yenisey/database verify        # прогон схемы на одноразовой базе
```

`pnpm build` и `pnpm dev` пишут в один и тот же каталог `apps/web/.next`, и
сборка затирает чанки работающего dev-сервера. Тот продолжает искать их в
памяти и валится сотнями `Cannot find module './855.js'` — выглядит как
поломка кода, хотя код цел. Лечение: остановить dev, `rm -rf apps/web/.next`,
запустить dev заново.

Если нужно собрать или поднять второй экземпляр, не трогая работающий dev,
каталог сборки переопределяется переменной `NEXT_DIST_DIR`:

```bash
NEXT_DIST_DIR=.next-diag npx next dev -p 3010   # из apps/web
```

Учтите, что Next при старте правит под себя `next-env.d.ts` и `include` в
`tsconfig.json`, подставляя туда этот каталог, — после диагностики оба файла
надо вернуть (`git checkout -- apps/web/next-env.d.ts apps/web/tsconfig.json`).

Проверить работающий API целиком, включая guard'ы и живой Postgres:

```bash
pnpm smoke              # 931 сценарий против поднятого API (с учёткой администратора)
pnpm db:clean-probes    # убрать заведённых им probe-*@example.com
```

Раздел про профиль клуба закрыт ролями, поэтому ему нужна учётка
администратора — без неё эти сценарии честно пропускаются с пояснением:

```bash
SMOKE_ADMIN_EMAIL=admin@club.ru SMOKE_ADMIN_PASSWORD="..." pnpm smoke
```

Без учётки идёт 142 сценария из 931, а итог всё равно пишет «провалов 0» —
смотрите на число, а не только на провалы.

Джоба автонеявки проверяется отдельной секцией, только по явной просьбе: API
поднимается с `ATTENDANCE_JOB=on ATTENDANCE_JOB_INTERVAL=10s`, а смоук
запускается с `SMOKE_AUTO_NO_SHOW=1` (863 сценария). На время секции срок
автонеявки клуба опускается до минуты — джоба закроет неявкой все
неотмеченные записи клуба в учётном окне, не только смоуковские. На базе
разработки это законно; настройки клуба секция возвращает.

Проверяются: регистрация и склейка ФИО, занятый email, чужой клуб, попытка
выдать себе роль владельца лишним полем, правила для ФИО и телефона, доступ
к защищённому маршруту без токена и с подделанным, вход, ротация
refresh-токена, обнаружение повторного использования, выход, публичное
название клуба и валидация формы. Отдельно — оба транспорта refresh-токена
(httpOnly-кука для браузера и тело ответа для мобильного клиента),
остановка подбора пароля, профиль клуба (залы со своими ценами, столы,
расписание — шаблон недели и правки на даты, тренер у занятия и клиент у
аренды), состав клуба с поиском и постраничной выдачей и бронирование стола
клиентом (сетка доступности, горизонт, цена с округлением получасов, отказ по
шагу зала, двойная бронь, отмена с фиксацией процента).

Брони смоук заводит в собственном зале проверки: за бронью стоит платёж,
внешний ключ стоит на `Restrict`, и стол с историей уже не удалить. Брони,
визиты и сам зал убирает `pnpm db:clean-probes` вместе с probe-учётками.
Журнал аудита он не трогает и не может: база отклоняет удаление из него, и
строки об отметках пробных клиентов в нём остаются.

`verify` разворачивает схему с нуля, накатывает ограничения целостности и
выполняет сценарии, которые проверяют, что база физически не даёт смешать
данные двух клубов. Направлять его можно **только** на пустую одноразовую
базу — он пишет туда заведомо некорректные данные.

## Проверки в CI

`.github/workflows/ci.yml` гоняет на каждый пуш и на каждый pull request три
независимые работы:

| Работа | Что делает |
|---|---|
| Типы, линт и тесты | `pnpm typecheck`, `pnpm lint`, `pnpm test` |
| Схема на чистой базе | `pnpm db:verify` против пустого Postgres 18 |
| Смоук по живому API | сид, демо-расписание, собранный API и `pnpm smoke` |

Работы не сцеплены нарочно: упавшие типы не должны прятать упавшую схему — за
один прогон видно всё.

Смоук в CI считается неудачей и тогда, когда он прошёл по сокращённой
программе. Без учётки администратора это 142 сценария из 931 при бодром
«провалов 0», и зелёная галочка на восьмушке проверок хуже красной — поэтому
учётка заводится прямо в прогоне, а строка «нет учётки администратора» в выводе
роняет работу.

В CI проходит 929 сценариев из 931: на чистой базе нет тренера с уже
**проведёнными** занятиями, и сводная проверка его статистики честно
пропускается. Демо-сид заводит только предстоящие.

Джоба автонеявки в CI не гоняется: ей нужен отдельный прогон с
`ATTENDANCE_JOB=on` и сдвинутыми настройками клуба.

## Переменные окружения

Все переменные валидируются при старте API (`apps/api/src/config/env.ts`) —
приложение падает сразу с внятным сообщением, а не через неделю на проде.
Отдельно проверяется, что `JWT_ACCESS_SECRET` и `JWT_REFRESH_SECRET`
различаются: при совпадении refresh-токен принимается как access и обходит
короткий срок жизни.

`.env` лежит в корне монорепозитория в единственном экземпляре и в git не
попадает; в репозитории только `.env.example`.

`ATTENDANCE_JOB` (`on`/`off`) включает джобу автонеявки. Не задана —
включена в production и выключена в разработке: иначе dev-сервер ставил бы
неявки демо-данным. `ATTENDANCE_JOB_INTERVAL` (по умолчанию `5m`) — как часто
она просыпается; неявку она ставит не раньше срока клуба, так что интервал
влияет только на запаздывание.

Уведомления в мессенджере MAX:

- `MAX_BOT_TOKEN` — токен бота из настроек на business.max.ru. Не задан — в
  разработке работает поддельный MAX (сообщения копятся в памяти, смотреть их
  — `GET /api/dev/max/sent?maxUserId=…`), в production уведомления выключены.
- `MAX_BOT_LINK` — адрес бота вида `https://max.ru/yenisey_bot`, обязателен
  вместе с токеном: к нему приписывается `?start=<токен привязки>`.
- `MAX_WEBHOOK_SECRET` — задан: события бот получает вебхуком на
  `<WEB_ORIGIN>/api/max/webhook` и сам подписывается на него при старте; не
  задан — опрашивает `GET /updates`. На машине разработчика публичного https
  нет, поэтому здесь его не задают.
- `NOTIFICATIONS_JOB` (`on`/`off`) — отправщик очереди и приём событий; как
  `ATTENDANCE_JOB`, включён только в production. Чтобы проверить настоящего
  бота с машины, задайте токен, ссылку и `NOTIFICATIONS_JOB=on`.
  `NOTIFICATIONS_JOB_INTERVAL` — как часто отправщик заглядывает в очередь
  (по умолчанию `10s`).
- `WEB_ORIGIN` — адрес сайта для ссылок в сообщениях; не задан — первый из
  `CORS_ORIGINS`.
- `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` — ключи
  уведомлений в браузер, задаются вместе: `npx web-push generate-vapid-keys`,
  контакт — `mailto:почта`. Не заданы — вне production пара заводится на
  время запуска, и браузер на машине подписаться может, но сообщения копит
  поддельный транспорт (`GET /api/dev/push/sent?endpoint=…`). Настоящая
  проверка в браузере требует ключей и `NOTIFICATIONS_JOB=on`.
- `PLATFORM_TIMEZONE` — пояс утренней сводки платформы (по умолчанию
  `Asia/Krasnoyarsk`): у платформы нет зала, а «за вчера» должно знать, где
  кончились сутки.

Сводку платформы в смоуке видит только владелец платформы: локально выдайте
роль учётке из `SMOKE_ADMIN_EMAIL` (`pnpm db:grant-platform`), иначе раздел 38
сводку платформы пропустит с пояснением. В CI роль выдаётся в прогоне.

## Почему pnpm 10, а не 11

На pnpm 11 установка пакетов с нативными бинарниками (`argon2`, `esbuild`,
`node-gyp-build`) падает с `ERR_PNPM_EPERM`: целевой каталог успевает
создаться пустым, а Windows не позволяет переименовать каталог поверх
существующего — даже пустого. Это гонка, зависящая от скорости тома: на
диске X воспроизводится стабильно, на C — нет. Версия закреплена в
`packageManager`; поднимать её до 11 без проверки не нужно.

Там же, в `package.json`, поле `pnpm.onlyBuiltDependencies`: pnpm 10 по
умолчанию не выполняет postinstall-скрипты зависимостей, а Prisma, argon2 и
sharp без них нерабочие.

## Миграции

Ограничения целостности, невыразимые в Prisma (exclusion-констрейнт на
пересечение броней стола, частичные уникальные индексы, check'и), лежат в
`packages/database/prisma/constraints.sql` и накатываются отдельной
миграцией `*_integrity_constraints`. При изменении этого файла нужно
завести **новую** миграцию, а не править применённую: Prisma сверяет
контрольные суммы и откажется работать с изменённой задним числом.

## Что уже реализовано

Сквозной сценарий авторизации: регистрация клиента → вход → защищённый
маршрут `/api/auth/me` → обновление пары токенов → выход.

**Профиль клуба** — раздел `/club`, доступный ролям `admin`/`owner`: название
и часовой пояс, минимальный шаг брони, цены аренды стола и отдельная сетка
цен «стол + робот», правила присутствия и неявки, список столов с
добавлением, переименованием и удалением. Стол с бронями удалить нельзя — за
бронями стоят платежи, и внешний ключ стоит на `Restrict`.

**Расписание зала** — там же, сеткой «время × столы» с 06:00 до полуночи.
Два режима: **шаблон недели** (`TableClosureRule`) описывает, как зал живёт
обычно, **расписание даты** (`HallDaySchedule` + `DayClosure`) правит
конкретный день и ЗАМЕНЯЕТ шаблон на эту дату целиком — иначе убрать одно
занятие в одну субботу было бы нечем. Пустое расписание правленого дня —
законное состояние, и заголовок `HallDaySchedule` нужен именно чтобы
отличить его от «день не трогали».

**Занятия и турниры** — раздел `/catalog`: типы тренировок («Общая
групповая», «Первая подача») с ценой и типы турниров со справочным
ограничением по рейтингу. Сам турнир там не заводится: его создаёт
постановка в сетку расписания — выбираете кисть «Турнир» и его тип,
закрашиваете время, и турнир появляется в списке уже с датой. Дата и время
начала берутся из сетки, вводить их дважды незачем.

В **шаблоне недели** турнир хранится ТИПОМ: «каждую субботу с 10:00 идёт
турнир» — законное описание жизни клуба, а конкретное проведение с датой
заводится, когда администратор открывает эту дату и сохраняет её расписание.
Конкретное проведение в шаблон не принимается — даты у повторяющегося окна
нет.

В клетке подписано, ЧЕМ она занята: название занятия или турнира, следом
тренер или арендатор. Цвет говорит, кто занят, а «просто тренировка» не
отличает детскую группу от «Первой подачи».

Назначения «другое» в палитре нет: оно ничего не объясняло ни администратору
через месяц, ни статистике. В enum значение остаётся — на него ссылаются уже
заведённые окна. Снятые с продажи
записи не удаляются, а гасятся: на них ссылается расписание, и удаление
упёрлось бы во внешний ключ.

У каждого окна есть назначение (аренда, спарринг, тренировка, робот, турнир,
другое) и закреплённый человек: у тренировки и спарринга — **тренер**, у аренды и
робота — **клиент**. У тренировки обязательны и тренер, и тип занятия: без
тренера оно не попадёт в его статистику, без типа клиенту непонятно, на что
он записывается, и неоткуда взять цену. Турнир возможен только в расписании
конкретной даты — у него дата и время, и в постоянном шаблоне недели ему
места нет; перекрёстные поля запрещены, а не просто необязательны —
тренер у аренды набрал бы чужие часы, а «закреплённый клиент» у тренировки,
где участников десяток, ввёл бы в заблуждение. Проверка стоит и в API, и
CHECK-констрейнтом в базе.

В сетке **цвет клетки — это человек**, а не назначение: тренеров и
арендаторов в расписании десятки, и различать их по подписи тяжело, а
назначений всего пять. Назначение обозначено буквой в углу клетки (А, С, Т,
Р) — буква читается на любом цвете, в отличие от второго цвета рядом.

**Состав клуба** — отдельный раздел `/people`, а не вкладка в настройках:
настройки правят изредка и осознанно, а список людей открывают по нескольку
раз в день, чтобы кого-то найти. Сотрудники и клиенты одним списком с
поиском по ФИО, почте и телефону; отключённые не пропадают, а помечаются.

Закрыто **только для клиента**: администратор посадить человека за такой
стол по-прежнему сможет, когда появится ручная бронь. Проверку выполняет
`apps/api/src/club/closures.ts`, и с появлением движка бронирования расписание
наконец начало на что-то влиять — до этого его звать было некому.

**Бронирование стола** — раздел `/booking`, доступный роли `client`: зал, день,
сетка «время × столы», выбор начала и длительности, цена до подтверждения.
Четвёртый сценарий ТЗ: клиент бронирует сам, без подтверждения администратора.
Свои брони и отмена — в кабинете.

Занятость в сетке склеена из двух источников — расписания зала и уже
заведённых броней — и отдаётся клиенту одним списком **без причины**:
расписание клуба его внутренняя кухня, а для выбора времени достаточно знать,
что стол занят.

Шаг сетки здесь — минимальный шаг брони зала, а не полчаса как в расписании:
администратор закрашивает крупными мазками, клиент выбирает ровно то, что зал
разрешает занять.

Тарификация идёт **начатыми получасами**: 80 минут аренды оплачиваются как 90.
Прайс задан ступенями («1 час — 400 ₽, далее +200 ₽ за каждые 30 минут»), а шаг
зала может быть десятиминутным — пропорциональный расчёт дал бы 533,33 ₽, цену,
которой нет ни на стене, ни в кассе. Минимум — час без робота и полчаса с
роботом: первые строки прайса, ниже которых цены не существует. Аренда «стол +
робот» идёт по своей сетке цен, а не наценкой поверх обычной.

Цену считает **сервер**, форма её только показывает (`GET /api/booking/quote`).
Второй расчёт на клиенте показывал бы сумму без запроса, но это деньги, и двух
мест, где они считаются, быть не должно.

Пересечение броней запрещено exclusion-констрейнтом Postgres, и последнее слово
за ним: два одновременных запроса оба увидят стол свободным, и развести их
проверкой в коде нельзя. Проверка в `booking/availability.ts` стоит ради
внятного ответа («стол в это время уже занят»), а не вместо базы.

Отмена фиксирует процент списания по политике клуба (`CancellationTier`) в поле
`chargeRatio` — **денег это пока не двигает**, платёжного шлюза нет. Процент
записывается именно для того, чтобы, когда шлюз появится, было от чего считать.

**Запись на занятия и турниры** — открытый список мероприятий клуба
(`/clubs/:slug`) и запись оттуда: у занятия есть лимит мест, у турнира его нет
вовсе. Лимит держит блокировка строки сессии (`SELECT … FOR UPDATE`), а не
констрейнт: «занято меньше, чем мест» — это подсчёт строк в другой таблице, и
двумя параллельными запросами он обходится. Состав записавшихся сервер
сокращает до «Фамилия И.» — полные имена чужих людей в браузер не уходят.

**Платформенный слой** — стартовая страница с поиском клуба по названию и
городу, «Мои клубы», лента ближайших мероприятий и «Мои записи» по всем клубам
сразу. Клуб открывается адресом `/clubs/:slug`; отмена всегда идёт клубным
маршрутом, потому что платформенный дубль разошёлся бы с ним в деньгах.

Оплаты за всем этим пока нет — см. «Известные ограничения каркаса».

Формы:

- ФИО спрашивается **тремя обязательными полями** и склеивается в
  `User.fullName` на сервере. В одно поле «ФИО» люди вписывают что
  придётся («Иван», «Иванов И.»), и администратор потом не может ни найти
  человека, ни обратиться к нему по имени;
- телефон вводится с **несъёмным «+7»**: префикс нарисован рядом с полем, а
  не лежит в его значении, поэтому стереть его нельзя. Вставка номера в
  любом виде («8-999-…», «+7 (999) …») превращается в десять цифр;
- **форма входа клуб не спрашивает вовсе**: аккаунт один на платформу, почта
  уникальна глобально. На регистрации клуб показывается официальным названием
  («АНТ «Енисей»») из открытого `GET /api/clubs/:slug` — код уходит в запрос
  сам и случайной правке не подлежит.

- пароли — argon2id (19 МиБ памяти, 2 прохода);
- access-токен JWT на 15 минут, refresh — 256 случайных бит на 30 дней,
  в базе только SHA-256 от него;
- **в access-токене только `sub`** — ни клуба, ни роли. Клуб приходит участком
  адреса (`/api/clubs/:slug/...`), роль в нём `ClubContextGuard` читает из
  `TenantMembership` на каждый запрос. Запрос к базе на каждый клубный маршрут
  — осознанная плата: снятая администратором роль перестаёт действовать сразу,
  а не через 15 минут;
- **запись в клуб не требует вступления в него**: человек без привязки
  проходит клубные маршруты как клиент, а `TenantMembership` заводится первой
  же бронью. Отключённый в клубе так вернуться НЕ может — guard отдаёт 403;
- **refresh-токен уезжает браузеру в httpOnly-куке**, а не в теле ответа:
  `SameSite=Lax`, путь сужен до `/api/auth`, `Secure` в production. В теле
  токен остаётся только по явному заголовку `X-Auth-Transport: body` — так
  его будет забирать мобильное приложение, у которого кук нет. Access-токен
  на клиенте живёт **только в памяти вкладки**: после перезагрузки страницы
  сессия восстанавливается обменом куки;
- **подбор пароля останавливается** после 10 неудачных попыток подряд по
  одной учётке (`AUTH_MAX_FAILED_ATTEMPTS`, окно `AUTH_ATTEMPT_WINDOW`).
  Считаются только провалы, ключ — почта, удачный вход обнуляет
  счётчик. Плюс грубый лимит `RATE_LIMIT` на весь API против заваливания
  запросами;
- ротация refresh-токена при каждом обновлении, с обнаружением повторного
  использования: предъявленный дважды токен гасит все сессии пользователя;
- `JwtAuthGuard` подключён **глобально** — по умолчанию закрыт каждый
  маршрут, открытые помечаются `@Public()`.

**Карточка человека и приём «с порога»** — `/clubs/:slug/people/:id`: сводка
по клубу (визиты, неявки, отмены, начислено, последний визит), история записей
с подписями отметок и визиты с порога. Новичка клуб не регистрирует за него: у
стойки QR на `/register?club=slug`, а уже зарегистрированного администратор
находит по точной почте или телефону и привязывает к клубу.

**Отметка присутствия** — на экране смены (`/clubs/:slug/desk`), только
администратор и владелец: «Требует отметки» по всему клубу, «Пришёл» одним
нажатием, «Не пришёл» со списанием по политике клуба или без него с причиной,
«Отметить всех пришедшими», исправление с причиной и история из журнала
аудита, визит с порога. Через сутки после окончания неотмеченное закрывает
неявкой джоба. После начала запись не отменяет никто — ни клиент, ни
администратор. Правила — `apps/api/src/attendance/attendance-rules.ts`.

**Профиль игрока** — «Кабинет» → «Профиль игрока» и публичная страница
`/players/:id` (сверх ТЗ, решение владельца от 12.09.2026): аватар, инвентарь,
достижения, разряд со сканом приказа. Разряд подтверждает администратор любого
клуба игрока из карточки человека; свой — нельзя, пересмотр чужого решения — с
причиной, всё в журнале аудита. До 16 лет страница видна только самому игроку
и администраторам его клубов. Правила — `apps/api/src/players/player-rules.ts`.

**Абонементы** — тарифы клуба (раздел «Занятия и турниры»), продажа у стойки
из карточки человека и автоматическое списание визита при записи на занятие
или турнир, которые тариф покрывает. Решения владельца от 19.09.2026: продаёт
администратор (онлайн-покупка появится вместе с ЮKassa), срок считается днями
до конца местного дня, возврат абонемента оформляется корректировкой баланса
до нуля с причиной.

**История абонементов** — раздел «Абонементы» в операционке
(`/clubs/:slug/subscriptions`): все движения визитов клуба подряд, с поиском по
фамилии владельца и переходом в его карточку. Раздел на чтение целиком, потому
что журнал только пополняется: ошибку правят новой корректировкой с причиной, а
не исправлением строки.

Продажа привязана к **залу**, а не к клубу (решение от 20.09.2026): по его
часовому поясу кончается срок, в его деньгах дня видна выручка. У клуба с одним
залом форма о зале не спрашивает и подставляет его сама; с несколькими зал
обязателен — иначе срок считался бы по чужим часам, а продажу показывала бы
каждая смена клуба.

Устройство: визит списывается в одной транзакции с записью и возвращается при
отмене — по мягкому правилу клуба всегда, по строгому только при ранней.
Неявка визит не возвращает: «сгорел» здесь и значит «не вернулся», отдельной
строки у сгорания нет, иначе исправленная отметка оставила бы в журнале ложь.
Журнал движений и остаток пишет одна функция под блокировкой абонемента.

Прайс «Енисея» из ТЗ (29 вариантов трёх тарифов) заводится `pnpm db:seed-demo`
— это цены клуба, а не устройство платформы, и в основном сиде им не место.

**Спарринг** — третий сценарий ТЗ: тренер берёт стол под занятие с учеником.
Той же страницей `/clubs/:slug/booking`, той же сеткой и тем же расчётом цены,
что у клиента, — отличается только владелец брони и подпись на экране. Свои
спарринги тренер видит там же, внизу страницы: в «Мои записи» они не попадают,
потому что это записи клиента, а не сотрудника. На смене такая бронь приходит
с пометкой «спарринг», и за столом в ней — сам тренер.

**Карточка тренера** — «Моя карточка» и «Мои группы» в клубе
(`/clubs/:slug/coach`) и публичная страница `/coaches/:id`: фотография,
достижения, инвентарь, ссылки на соцсети и стоимость занятий. Карточка одна на
все клубы, где человек тренирует, а цены — свои в каждом: на «Моей карточке»
это две формы, карточка (платформенный маршрут `/me/coach-card`) и цены клуба
(`clubs/:slug/coach/prices`). Правит обе только сам тренер; администратор видит
их в карточке человека и не трогает. «Мои группы» показывают предстоящие
занятия с составом: полное имя и телефон, чтобы было кому позвонить; отметок и
денег там нет — это работа администратора на смене.

**Статистика тренера** — в «Моих группах» у тренера и в его карточке у
администратора, одним расчётом: сколько занятий проведено за 30/90/365 дней
или за всё время, посещаемость, сколько человек приходит в среднем и
насколько заполнены группы. Посещаемость считается только по отмеченным
записям; неотмеченные показаны отдельно, потому что это недоработка смены, а
не прогул.

До 20.09.2026 карточка принадлежала клубу целиком, и правил её в том числе
администратор — так написано в ТЗ. Решением владельца это разделено: рассказ о
себе принадлежит человеку (`CoachCard`, ключ `userId`), клубу остались деньги
(`CoachProfile` — пара «человек + клуб»). Правка чужой карточки снята вовсе:
из «Енисея» нельзя менять то, что тренер показывает соседнему клубу. Публичная
страница от этого выпрямилась — клубы на ней перечислены списком, каждый со
своей ценой, и компромисса «показываем самую свежую карточку» больше нет.

**Родитель и ребёнок** (сверх ТЗ, решения владельца от 12.09 и 17.09.2026) —
«Кабинет» → «Мои дети»: завести учётку ребёнку, закрепить существующую по
почте (подтверждает ребёнок у себя в кабинете), сменить ребёнку пароль,
отвязать. Дальше на странице клуба, в брони стола, в «Моих записях» и в
кабинете переключатель «Действую за: себя / ребёнка» (`?for=` в адресе).
Ребёнок младше 16 сам не записывается и не отменяет. У стойки — блок «Семья»
в карточке человека: завести ребёнка родителю, предложить родителя, снять
закрепление с причиной. Правила — `apps/api/src/guardianship/guardianship-rules.ts`.
Проверить руками проще всего на пробных учётках: родителю нужна дата рождения
старше 18 лет, ребёнку — младше 16.

## Известные ограничения каркаса

- **Интеграционных тестов денежных путей нет** (решение владельца от
  21.09.2026: отложено до CI на хостинге). Сейчас деньги закрыты с двух сторон:
  чистые правила под `node --test` (`pricing`, `attendance-rules` с
  `noShowRatio`, `subscription-rules`, `revenue`, `person-summary`) и смоук по
  живому API. Между ними остаётся щель — то, чего смоук не достаёт по времени:
  - **неявка спарринга** (100 % аренды): бронь нельзя начать раньше ближайшего
    шага сетки, а ждать этого шага прогон не может. Правило закрыто тестом
    `noShowRatio`, но связка «отметка → запись в базе» — нет;
  - **джоба автонеявки** идёт только отдельным прогоном
    (`SMOKE_AUTO_NO_SHOW=1`) и в обычный не попадает;
  - **гонки и откаты транзакций**: смоук ловит только те, что успевает
    устроить двумя параллельными запросами.

  Когда появится CI, эту щель закрывает харнесс на одноразовой базе — той же,
  что у `verify`.
- **Счётчик неудачных попыток входа живёт в памяти процесса.** Для одного
  экземпляра API этого достаточно; когда экземпляров станет несколько, окно
  придётся перенести в общее хранилище (Redis), иначе лимит умножится на
  число процессов.
- **Файлы лежат в Postgres.** Аватары и сканы приказов — колонкой `bytea` за
  интерфейсом `FileStorage`: объектного хранилища нет, пока нет хостинга.
  Растёт резервная копия базы; переезд в S3 — новая реализация `FileStorage`
  и одна строка `useClass` в `FilesModule`.
- **Картинки пережимает `sharp` в процессе API** — сотни миллисекунд
  процессора на загрузку. Загрузки ограничены 20 в минуту с одного адреса; при
  росте нагрузки пережатие стоит вынести в очередь.
- **Логотип отрисован вручную.** Знак в `LogoMark` набран по растровым
  файлам брендбука, оригинального вектора в репозитории нет. Там же на глаз
  снят изумруд `--brand-600`. Подробнее — `docs/DESIGN.md`.
- **Телефон и дата рождения обязательны у всех ролей.** У сотрудников,
  заведённых до этого правила, их неоткуда взять, и миграция подставила
  заметные заглушки — `+70000000000` и `01.01.1900`. Их видно в составе клуба
  с первого взгляда, и администратор должен их заменить.
- **Тренерам, администраторам и владельцу ФИО проставлено плейсхолдером.**
  Миграция `20260826060000_user_full_name` перенесла имена клиентов из
  `ClientProfile`, но у остальных ролей их раньше просто не хранили — там
  стоит «Имя не указано». Проставить настоящие сможет администратор клуба,
  когда появится экран управления сотрудниками.
- **Отчество обязательно.** У иностранцев и части народов России его нет в
  паспорте. Требование введено осознанно — чтобы люди не игнорировали поле,
  — но при появлении таких клиентов его придётся ослабить.
- **Оплаты за бронью нет.** Бронь заводится со статусом `BOOKED` и посчитанной
  ценой, но холд в ЮKassa не ставится: нужны оферта и платёжный шлюз. До тех
  пор `chargeRatio` при отмене и отметке записывается, а деньги не двигаются.
- **Уведомления — в MAX и в браузере.** ТЗ называет Telegram и Web Push;
  вместо Telegram выбран MAX — решение заказчика от 23.09.2026. Напоминание
  об отметке через час приходит тем администраторам, кто подключил хоть один
  канал; остальные по-прежнему видят «просрочено» на экране смены.
- **На iPhone уведомления в браузере — только с экрана «Домой».** В обычной
  вкладке Safari их нет вовсе; карточка в кабинете так и пишет. Манифеста
  приложения у сайта пока нет, и значок на экране «Домой» — снимок страницы.
- **Настоящий браузер смоук не проверяет.** Подписка, доставка и отозванная
  подписка проверяются через поддельные службы push; что service worker
  отдаётся сайтом и регистрируется, проверено вручную в Chrome 24.09.2026.
  Разрешение на уведомления автоматизированный браузер не выдаёт — полный
  путь с настоящим уведомлением проверяется руками на стенде.
- **Перенос брони администратором клиенту не сообщается** — решение
  владельца от 24.09.2026: переносящий бронь администратор звонит сам.
  Напоминание при этом придёт по новому времени.
- **Неявка, абонемент и разряд в смоуке не проверяются**, только юнит-тестами
  текстов и правил: дождаться начала занятия в пределах прогона нельзя, а
  продажа абонемента и проверка разряда — долгая подготовка ради одной строки
  вызова.
- **Горизонт бронирования — константа в 14 дней** (`BOOKING_HORIZON_DAYS` в
  `packages/types/src/booking.ts`). В ТЗ горизонта нет, а без него бронь уехала
  бы на время, под которое расписание ещё не составлено. Когда клубам
  понадобятся разные горизонты, это станет полем в `Tenant` и строкой в форме
  настроек.
- **Часы работы клуба отдельным полем не хранятся.** Сетка бронирования идёт с
  06:00 до полуночи теми же константами, что и сетка расписания. Бронь,
  переходящая за полночь, невозможна — она попала бы в другие сутки, где
  действует уже другое расписание.
- **Абонемент не покрывает аренду стола.** Флаги тарифа в схеме есть
  (`coversTableRental`, `tableRentalUnlimitedOnly`), но правило не написано:
  бронь стола — отдельный поток со своей ценой по длительности. В форме тарифа
  этих флагов пока нет вовсе, чтобы не обещать несуществующего.
- **Безлимитный абонемент ничем не рискует при неявке.** Визитов у него нет,
  и сгорать нечему; ТЗ санкции не описывает.
- **У спарринга нет ученика.** Бронь принадлежит тренеру, и с кем он играет,
  платформа не хранит: `TableBooking` несёт либо клиента, либо тренера, и это
  держит CHECK. Записать ученика значило бы завести вторую бронь на тот же
  стол.
- **Пробные учётки абонементов не убираются.** Журнал абонементов — только
  вставки, без исключений, поэтому клиента и тренера, на чьи записи он
  ссылается, `clean-probes` удалить не может: он их считает и называет числом.
  Смоук поэтому ведёт абонементы под постоянными учётками
  (`probe-subscriptions@example.com`, `probe-subscriptions-coach@example.com`) и
  постоянным тарифом — остаток копится один раз, а не с каждым прогоном.
- **Файлы раздаёт контроллер профиля игрока.** `PlayerFilesController` отдаёт и
  аватар, и скан приказа, и фотографию тренера, решая доступ по виду файла.
  Появится четвёртый вид — раздачу стоит вынести в `FilesModule` с политикой на
  вид; ради одной ветки `return true` это было бы преждевременно.
