### Session (15:16) - ТЗ платформы «Енисей»: пересборка в SaaS для клубов настольного тенниса

**Context:** Продолжение работы над `docs/TZ.md` — техническим заданием на
веб-приложение для академии настольного тенниса «Енисей». В начале сессии
владелец клуба Андрей Шулепин прислал серию сообщений в мессенджере, которые
кардинально меняли рамку проекта, и сессия была посвящена разбору этих
сообщений, доуточнению деталей через диалог и финальной пересборке ТЗ в
чистый документ для согласования с руководством.

**Key Exchanges:**
- Андрей описал продукт как три «движка»: бронирование/оплата услуг
  (мероприятия vs вещи), CRM с персданными, проведение турниров и рейтинг —
  и сообщил, что Этап 1 должен приносить деньги как можно быстрее через
  подписочную модель для клубов (SaaS), а не только обслуживать «Енисей».
- Обсуждали и решали десятки уточняющих вопросов: механику спарринга (аренда
  стола тренером), модель биллинга подписки клуба (ЮKassa автоплатежи + своя
  джоба, без стороннего провайдера), тарифы платформы (5000₽/мес, 50000₽/год,
  130000₽/3 года), политику отмены записи «как в такси» (холд карты →
  списание 0/50/100% по времени отмены), эскалацию неотмеченного присутствия
  (push через час, автонеявка через сутки), флоу оплаты наличными «с порога»
  для незарегистрированных клиентов с последующей ручной привязкой визита.
- Получены и разобраны реальные прайс-листы «Енисея» (флаеры) с ценами на
  тренировки, турниры, аренду стола (в т.ч. с роботом) и три плана
  абонементов с разным покрытием услуг и общим счётом визитов.
- Получен список из 6 базовых типов турниров клуба (Абсолют, Клуб 50/100/
  200/300, Пятничное турне) — решено, что рейтинг-число в названии турнира
  сейчас чисто справочное, без проверки/блокировки (актуальный рейтинг
  получать неоткуда).
- Добавлен новый сценарий: публичная карточка тренера (фото, достижения,
  инвентарь, цены, соцсети).
- В финале сессии документ полностью переписан набело: убраны все пометки
  вида «уточнено 15.08.2026», «по итогам сообщений», журнал изменений — ТЗ
  приведено к виду презентабельного документа для согласования с
  руководством.

**Decisions Made:**
- Продукт — тиражируемый SaaS для клубов настольного тенниса с первого
  этапа, «Енисей» — пилотный клуб без оплаты подписки; мультиарендность
  (`tenant_id`) и настраиваемость профиля клуба — рабочее требование Этапа 1.
- Этап 1 = движок бронирования/оплаты (тренировки, турниры, спарринги, аренда
  стола/робота) с настраиваемым профилем клуба + подписочный доступ для
  клубов. Этап 2 = продажа инвентаря. Этап 3 = модуль тренировочных групп
  «спортшкола».
- Оплата клиента — двухстадийная (холд карты при записи → списание по факту
  отметки присутствия администратором), для абонемента — более мягкая
  политика (визит сгорает только при неявке без отмены).
- Наличная оплата — только для первого визита нового клиента «с порога», не
  альтернативный способ оплаты для зарегистрированных клиентов.
- Рейтинг участника — необязательное справочное поле, без расчёта и без
  проверки допуска на текущем этапе; тема отложена до появления источника
  актуальных данных.
- Схема заморозки/списания денег требует отдельного юридического документа
  (оферта/пользовательское соглашение) — это отдельная задача с юристом, не
  входит в разработку кода.

**Lessons Learned:**
- Устные сообщения владельца бизнеса в мессенджере часто описывают
  архитектурную рамку и роудмап очень сжато («три движка», «этапы») — важно
  разворачивать их в явные пользовательские сценарии и модель данных, задавая
  уточняющие вопросы, а не додумывать детали самостоятельно.
- При итеративном сборе требований черновик документа стоит держать с
  пометками дат/источников уточнений (для прослеживаемости в моменте), но
  перед финальной подачей руководству — обязательно вычищать весь этот
  служебный шум, оставляя только формулировки решений.
- Флаер/прайс-лист с «чужим» названием в шапке («Пироги» вместо «Енисей») не
  всегда ошибка — стоит спросить прежде, чем предполагать баг в документе
  клиента.

### Session (19:13) - Проектирование и проверка схемы БД «Енисея»

**Context:** Следующий шаг после ТЗ — детальная схема БД. За сессию схема
прошла путь от первого черновика до утверждённой структуры, проверенной на
живом PostgreSQL: ревью на уязвимости, три волны исправлений, прогон тестов.

**Key Exchanges:**
- Составлена Prisma-схема по модели данных из ТЗ, затем добавлены подробные
  комментарии на русском по просьбе владельца проекта.
- По запросу проведён аудит схемы на уязвимые места: найдено ~28 проблем,
  разбитых на критичные / средние / мелкие. Разбирались тремя заходами.
- Владелец заметил в тексте несогласованное значение (ступень отмены 30%) и
  спросил, откуда оно взялось. Признано: число выдумано как иллюстрация, а
  сама идея настраиваемой политики отмены — тоже достройка требований,
  поданная как «пункт списка проблем».
- Обсуждался объём схемы (28 таблиц): разобрано, что 18 следуют из ТЗ, 10
  добавлены при ревью, максимальное осмысленное сокращение — до 25.
  Предложение разбить внедрение на волны отклонено.
- Обсуждался вопрос локальной разработки против сразу-хостинга.

**Decisions Made:**
- Изоляция клубов — на составных внешних ключах: tenantId продублирован во
  все дочерние таблицы, связи идут по паре (id, tenantId). Postgres
  физически не принимает бронь с сессией одного клуба и клиентом другого.
  Postgres RLS отклонён как избыточный на текущем этапе.
- Все денежные суммы хранятся в копейках (Int).
- Удаление по умолчанию запрещено (onDelete: Restrict на всех связях);
  «удаление» клиента — это deactivatedAt/anonymizedAt, а не DELETE.
- Политика отмены вынесена в настройку клуба (CancellationTier) — решение
  уровня продукта, в ТЗ политика фиксированная; значения «Енисея» не менялись.
- Тарифы платформы вынесены в таблицу PlatformPlan с фиксацией цены покупки.
- Структура БД утверждена в текущем виде: 28 таблиц, Prisma 6.x.
- Хостинг не покупается сейчас: разработка локально, VPS поднимается к
  моменту интеграции платежей (нужен публичный HTTPS под вебхуки ЮKassa).

**Lessons Learned:**
- Расширение бизнес-правил за пределы ТЗ нужно согласовывать ДО реализации.
  Поданное как «найденная проблема», такое расширение проскакивает без
  обсуждения, и решение оказывается принятым задним числом.
- Выдуманные для иллюстрации значения (проценты, суммы) неотличимы в коде и
  комментариях от согласованных требований — либо помечать, либо не вводить.
- Тесты на констрейнты в блоке EXCEPTION WHEN others засчитывают ЛЮБУЮ
  ошибку, включая ошибку не по той причине. Проверять нужно код ошибки и имя
  ограничения через GET STACKED DIAGNOSTICS, иначе «22 из 22 прошли» ничего
  не доказывает.
- Ограничения, невыразимые в Prisma (exclusion-констрейнты, частичные
  уникальные индексы, check'и), выносятся в raw-SQL миграцию. Проверка в коде
  от гонок не спасает: два параллельных запроса увидят стол свободным.
- Docker Hub с рабочей машины недоступен (TLS-таймаут), зеркало gcr.io тоже.
  Это влияет на план деплоя: доступность реестра с сервера нужно проверять
  до первого выката.
- Prisma допускает участие одной колонки (tenantId) сразу в нескольких
  составных связях — проверено валидатором, не очевидно из документации.
- Схема валидна на Prisma 6.x; на Prisma 7 падает — там url из datasource
  переехал в prisma.config.ts.
