# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это за репозиторий

«Енисей» — SaaS-платформа для клубов настольного тенниса. Один продукт, один язык: TypeScript под pnpm 10 + Turborepo, Postgres 18. Документация — в `docs/`, обзор и быстрый старт — в `README.md`.

До 01.09.2026 под этим же корнем жил внешний проект — компилятор памяти на Python (`scripts/`, `hooks/`, `daily/`, `knowledge/`, `AGENTS.md`, `pyproject.toml`). Он снят: долгую память ведёт claude-mem, хранящий базу вне репозитория, в `~/.claude-mem/`. Если в старом коммите или в чужой ссылке встретится `uv run python scripts/compile.py` — этого больше нет, искать в истории git.

## Команды

Продукт (pnpm 10 + turbo, из корня):

```bash
pnpm dev            # apps/api и apps/web в watch-режиме
pnpm typecheck      # по всем пакетам
pnpm test           # node --test
pnpm smoke          # 767 сценариев против поднятого API и живого Postgres (нужны SMOKE_ADMIN_*)
pnpm db:migrate     # prisma migrate dev
pnpm db:studio
pnpm db:create-admin -- --email a@club.ru --password "..." --name "Иванов Иван"
pnpm db:seed-demo   # занятия и турниры на ближайшие дни (отдельно от сида: даты протухают)
```

Модули, которые гоняются через `node --test`, **не могут иметь относительных
импортов**: node требует расширение `.ts`, а сборка (`tsconfig.build.json`,
`allowImportingTsExtensions: false`) его не принимает. Поэтому чистые модули
вроде `club/closures.ts` и `booking/availability.ts` самодостаточны, а всё
внешнее приходит в них аргументами.

Один тест — напрямую, минуя turbo:

```bash
cd apps/api && node --test --experimental-strip-types src/auth/tokens.test.ts
```

Проверка схемы БД на одноразовой базе:

```bash
pnpm --filter @yenisey/database verify
```

`verify` разворачивает схему с нуля и намеренно пишет некорректные данные, проверяя, что база физически не даёт смешать данные двух клубов. **Направлять только на пустую одноразовую базу.** После `pnpm smoke` остаются учётки `probe-*@example.com` — убираются через `pnpm db:clean-probes`.

Те же проверки идут в CI на каждый пуш (`.github/workflows/ci.yml`): типы с линтом и тестами, схема на пустом Postgres 18 и смоук по собранному API. Две вещи, которые там сделаны намеренно и которые легко сломать: **смоук по сокращённой программе считается провалом** (без учётки администратора идёт 85 сценариев из 767, а итог всё равно бодро пишет «провалов 0»), и **`verify` падает на проваленном сценарии** — до 22.09.2026 он печатал «ПРОВАЛ» и возвращал ноль. Подробности — в `docs/DEVELOPMENT.md`.

## Архитектура продукта

`apps/api` — NestJS. Модули `auth`, `tenants`, `users`, `club`, `booking`, `events`, `entries`, `me`, `desk`, `attendance`, `people`, `files`, `players`, `coaches`, `subscriptions`, `guardianship`, `prisma`, `config`. `apps/web` — Next.js (app router). `packages/database` — Prisma, единственный владелец схемы. `packages/types` — общие типы, собирается через `tsc -p tsconfig.build.json`.

Клиент Prisma генерируется в `packages/database/generated/` и **в git не попадает** — после свежего клона и после правки схемы нужен `pnpm db:generate`, иначе типы не сойдутся.

### Мультиарендность — главное ограничение

Изоляция клубов держится на составных ключах и проверяется на уровне БД, а не только в коде. Точка входа человека в схему — не `User`, а `TenantMembership` (см. ниже). Правила схемы, которые нельзя нарушать:

- **Деньги — целые числа в копейках.** Не рубли с дробной частью. Конвертация только на границе представления.
- **Цену услуги считает сервер, и только он.** Форма показывает то, что вернул `GET /api/booking/quote`. Второй расчёт на клиенте разойдётся с первым молча.
- **Аренда тарифицируется начатыми получасами**, минимум — час без робота и полчаса с роботом. Логика — `apps/api/src/booking/pricing.ts`, там же тесты на прайс «Енисея».
- **Удаления нет.** Клиент деактивируется через `deactivatedAt`/`anonymizedAt`; на внешних ключах `onDelete: Restrict`.
- **Часть ограничений живёт в raw SQL.** `packages/database/prisma/constraints.sql` — 78 CHECK, 8 частичных уникальных индексов, 3 EXCLUDE (пересечение броней, шаблона недели и расписания дня) и четыре триггера, запрещающих правку и очистку двух журналов — аудита и абонементов. Prisma такое не выражает, поэтому при изменении схемы этот файл правится руками отдельно от миграции — и сверяется с базой: `verify` разворачивает схему из файла, и ограничение, которое есть только в миграции, он не проверяет (так два правила окон дня выпали из проверки до 12.09.2026).
- **Цены, шаг брони и часовой пояс — у зала (`Hall`), а не у клуба.** Залы одной организации бывают в разных регионах, и общий на клуб пояс сдвинул бы в одном из них границы операционного дня и порог «за час до начала», от которого считаются деньги. У клуба остаётся то, что составляет договор с клиентом: политика неявки и правила абонемента.
- **Город указывается и у клуба, и у зала**, из справочника `City`, а не строкой. Поиск на стартовой странице находит клуб, если совпал **город клуба ИЛИ город хотя бы одного его зала** — правило ломается тише всего, поэтому оно закрыто смоук-сценарием, а не только типами.
- **Своих клубов не больше трёх.** Предел выражен структурой `UserClub`: слот уникален в пределах человека и ограничен диапазоном 1..3, поэтому четвёртый клуб физически некуда положить. Проверка в сервисе от гонки не спасает.

Сценарии на изоляцию — `packages/database/prisma/tests/schema-tests.sql`.

### Единый аккаунт: человек входит в схему через `TenantMembership`

`User` — **глобальная учётная запись платформы**. Клубу не принадлежит, роли
не несёт, почта уникальна по всей платформе. Всё клубное висит на
`TenantMembership` — паре «человек + клуб», которая несёт роль и клубное
отключение. Именно она, а не `User`, — мишень составных внешних ключей:
цепочка «бронь → анкета → привязка → (человек, клуб)» стала на звено длиннее,
но база по-прежнему не примет бронь со столом одного клуба и клиентом другого.

Что из этого следует при чтении кода:

- **Роли «вообще» нет.** `role` в профиле отсутствует; спрашивать роль без
  указания клуба бессмысленно. На сервере её даёт `ClubContextGuard`, на вебе —
  `roleInClub()` из `apps/web/src/lib/membership.ts`.
- **Клуб приходит участком адреса**, а не токеном: `/api/clubs/:slug/...`.
  Access-токен несёт только `sub`. Плата — запрос к базе на каждый клубный
  маршрут; выигрыш — снятая роль действует сразу, а не через 15 минут.
- **Порядок guard'ов в `auth.module.ts` единственно возможный**: токен →
  клубный контекст → роль. Перестановка даёт следующему guard'у пустоту.
- **Отключений два.** `User.deactivatedAt` — не пускает на платформу вовсе;
  `TenantMembership.deactivatedAt` — закрывает один клуб. Уволенный тренер
  «Енисея» продолжает играть в соседнем клубе.
- **Вступать в клуб, чтобы записаться, не нужно.** Человек без привязки
  проходит клубные маршруты как клиент, а `TenantMembership` заводится первым
  действием — см. `ensureClientMembership` в `booking.service.ts`. Проверять
  `joined`, а не только `role`, нужно везде, где сервис собирается писать.
- **Анкеты ролей ключуются парой** `(userId, tenantId)`, а не одним `userId`:
  один человек законно является клиентом в трёх клубах.

Миграция `20260902100000_platform_account` данные сохраняет и **сливает учётки
с одинаковой почтой**, оставляя самую свежую по `updatedAt`; все refresh-сессии
она гасит — формат токена изменился.

### Платформенный слой над клубами

Стартовая страница платформы клуба не имеет: на ней поиск по названию и
городу, а клуб открывается адресом `/clubs/:slug`. Отсюда несколько правил,
которые легко нарушить незаметно:

- **`TENANT_SLUG` больше не участвует в запросах.** Клуб приходит из адреса
  страницы: `clubApi(slug)` в `apps/web/src/lib/api.ts`, а страницы берут код
  хуком `useClubApi()`. Переменная окружения осталась запасным значением для
  разработки.
- **Карточка клуба отвечает на вопросы посетителя, а не только называет клуб.**
  `GET /clubs/:slug` (открыт) отдаёт контакты и залы с адресами и ценами, а
  страница показывает их блоком «Где играют» с кнопкой аренды. До 21.09.2026
  там была одна лента мероприятий: человек, нашедший зал в поиске, не мог
  узнать ни адреса, ни цены, ни телефона, а сама аренда была достижима только
  через пункт шапки, который виден уже состоявшемуся клиенту КЛУБА — то есть
  новичку сценарий ТЗ «клиент бронирует сам» был закрыт. Цены в карточке — те
  же поля зала, что считает бронь: второй прайс «для витрины» разошёлся бы с
  настоящим на первой же правке.
- **Открытый маршрут не значит анонимный.** `JwtAuthGuard` на `@Public()`
  всё равно разбирает предъявленный токен и просто не отказывает, когда его
  нет. Без этого открытый список мероприятий не мог бы ответить вошедшему на
  вопрос «а я записан?».
- **Обновление сессии — single-flight** (`refreshOnce` в `lib/api.ts`).
  Refresh-токен ротируется, а повторное предъявление отозванного сервер
  считает кражей и гасит ВСЕ сессии человека. Два параллельных обмена одной
  кукой (шапка и страница спрашивают профиль одновременно) выбрасывали из
  аккаунта во всех вкладках. Любой новый способ обновить сессию обязан идти
  через это же обещание.
- **Мероприятий два вида — занятия и турниры.** Различает их поле `kind` у
  `ClubEvent` и `BookingEntry`, и по нему же веб выбирает маршрут записи:
  `trainings/:id/booking` против `tournaments/:id/registration`. Сборка строки
  мероприятия — одна на всех, `apps/api/src/events/event-view.ts`: её зовут и
  открытый список клуба, и лента на стартовой странице, и разойтись им нельзя.
- **Клиента у окна расписания нет.** Он там был — «закреплённый арендатор», —
  и это оказалось ловушкой: окно не несёт ни цены, ни статуса, ни отмены, а
  человек, которого администратор вписал кистью «Аренда», считал себя
  записанным и не видел записи в кабинете. Время, занятое человеком, — это
  `TableBooking`. В расписании даты кисть аренды с выбранным клиентом заводит
  бронь (протяжка → подтверждение с ценой от сервера), в шаблоне недели
  клиента нет вовсе. Сетка дня показывает брони занятыми клетками только для
  чтения.
- **Занятие и турнир заводятся в расписании зала, а не формой.** Администратор
  выбирает кисть, тип, тренера и число мест и закрашивает время; при сохранении
  дня `resolveEvents` в `apps/web/src/app/clubs/[slug]/schedule/dayEvents.ts`
  создаёт `TrainingSession` (одно на пару «тип + тренер», границы — по всем
  закрашенным окнам) и `Tournament` (один на тип и дату). В шаблоне недели ни
  того, ни другого быть не может: у них конкретная дата, а шаблон повторяется —
  там остаются только типы.
- **Занятие заводится только по окнам, которых администратор коснулся в этой
  правке** (`markTouched` в `closureGrid.ts`). Отвязанный от шаблона день полон
  окон с типом тренировки, но без занятия, и без этого условия правка одной
  клетки аренды открыла бы запись сразу на все группы из шаблона. Турниры
  заводятся по всем окнам — окно турнира в дне обязано ссылаться на проведение
  (`DayClosure_attachments_match_purpose`).
- **Отвязка дня от шаблона — отдельное действие**, `POST .../days/:date/detach`,
  а не побочное следствие «Сохранить». Раньше неправленый день отвязывался
  первым же сохранением, даже без правок. Правка дня и возврат к шаблону сами
  убирают занятия и турниры, оставшиеся без окна и без записей
  (`dropOrphanedEvents` в `schedule.service.ts`).
- **Лимит мест держит блокировка строки, а не констрейнт.** Проверка «занято
  меньше, чем мест» требует подсчёта строк в другой таблице, и двумя
  параллельными запросами обходится. `registerForTraining` берёт
  `SELECT ... FOR UPDATE` по сессии — рецепт записан в `constraints.sql`,
  раздел 4. У турнира лимита мест нет вовсе.
- **Состав записавшихся сокращает сервер.** `shortName` живёт в
  `packages/types`, потому что применяют его обе стороны; полные имена чужих
  людей в браузер не уходят.
- **Список записей живёт в одном месте.** `EntriesService` собирает и «Мои
  записи» по всем клубам, и блок «Мои мероприятия» на странице клуба. Отмена
  идёт клубным маршрутом: платформенный дубль разошёлся бы с ним в деньгах.
- **Аренда стола попадает в «мои», но не в публичные списки**: к чужой броне
  стола нельзя присоединиться.

### Отметка присутствия

За отметкой стоят деньги: неявка списывает процент клуба, присутствие — всю
цену. Правила, которые легко нарушить незаметно:

- **Правила отметки — чистая функция `decideMark`**
  (`apps/api/src/attendance/attendance-rules.ts`, под тестами). Отмечать можно
  с момента начала, верхней границы нет; первая отметка — без причины,
  исправление и прощение неявки — только с ней; вернуть в «не отмечено»
  нельзя. Повтор ничего не меняет и в журнал не пишет.
- **Одна отметка — одна транзакция** (`AttendanceService.applyInTx`): строка
  записи под `FOR UPDATE`, статус и процент, один `VisitLog` на запись
  (исправление его обновляет) и строка `AuditLog`. Процент — снимок политики
  на момент отметки, как `priceAtBooking` — снимок цены.
- **Отмена после начала запрещена всем** (`cancellationOpen`). Без этого
  пропустивший отменял задним числом и платил позднюю отмену вместо неявки.
  Все отмены и джоба пишут условным обновлением `WHERE status = 'BOOKED'`.
- **Бронь, которую администратор заводит после начала, сразу «пришёл»** —
  начало по шагу зала почти всегда чуть в прошлом, и без этого её закрыла бы
  неявкой джоба.
- **Джоба автонеявки** (`AutoNoShowJob`) не трогает то, что закончилось
  раньше `Tenant.attendanceTrackedSince`: до отметки в продукте всё прошедшее
  так и осталось «записан». В разработке она выключена (`ATTENDANCE_JOB`).
- **«Требует отметки» собирает сервер по всему клубу**, а не лента дня зала:
  мероприятия без сетки и вчерашнее лента не видит. Мероприятия дня без сетки
  экран смены получает отдельно (`unplaced`).
- **`AuditLog` — только вставки**, это держит триггер. `clean-probes` его не
  чистит и не может.
- **У записи на мероприятие два идентификатора**: `id` — занятия или турнира
  (по нему отмена), `entryId` — строки записи. После «отменил и записался
  снова» строк две, и ключ списка и поиск записи идут по `entryId`.

### Люди клуба

- **Карточка человека — один запрос**: `GET clubs/:slug/people/:id` отдаёт
  человека, сводку, записи и визиты сразу. Записи собирает тот же
  `EntriesService`, что и «Мои записи», деньги считает тот же `chargeOf`, что
  и итог дня на смене: второй расчёт разошёлся бы с первым молча.
- **Сводка считается по всем записям, а не по показанной сотне** — «не пришёл
  трижды» не должно меняться от того, сколько строк влезло на экран. Правила —
  чистая `personSummary` под тестами.
- **Учётку за человека клуб не заводит.** Новичок регистрируется сам по QR у
  стойки (`/register?club=slug` — такая регистрация сразу привязывает к
  клубу), а администратор находит уже зарегистрированного и привязывает
  (`people/lookup` + `people/:id/attach`). Пароля чужой учётки клуб знать не
  должен, а восстановления пароля в продукте пока нет. Единственное
  исключение — учётка ребёнка младше 16 у стойки: почту и пароль задаёт
  родитель, который стоит рядом (`POST people/:id/children`).
- **Поиск человека — только точный и по одному полю**, с отдельным
  ограничением частоты; до привязки имя отдаётся сокращённым. По куску почты
  можно было бы перебрать людей чужих клубов.
- **Телефон в схеме не уникален** (у семьи он один на всех), поэтому поиск по
  телефону при нескольких совпадениях отвечает «несколько человек», а не
  первым попавшимся: привязать не того — значит писать ему чужие визиты и
  списания.

### Профиль игрока

Расширение сверх ТЗ (решение владельца от 12.09.2026): аватар, инвентарь,
достижения, спортивный разряд с проверкой клубом. Правила, которые легко
нарушить незаметно:

- **Профиль висит на `User`, а не на `TenantMembership`.** Заполняет его
  только сам человек (`/me/player`); клуб профиль не правит, а решает по
  разряду (`POST clubs/:slug/people/:id/rank/review`).
- **Правила — чистые функции** в `apps/api/src/players/player-rules.ts`, под
  тестами: кому виден профиль и файл, как правка сбрасывает подтверждение,
  когда нужна причина. Настоящая правка разряда — снова `PENDING` и стёртая
  подпись; повтор того же — ничего.
- **Свой разряд не подтверждает никто** — CHECK `SportRank_not_self_review`,
  а не только сервис. Проверяющий ссылается на `TenantMembership` составным
  ключом: база не примет решение от человека не из того клуба, что в подписи.
- **Решение принимается о версии**: админ присылает `version` разряда, и
  обновление идёт условием по `updatedAt`. Игрок поправил разряд, пока админ
  смотрел карточку, — 409, а не подтверждение непросмотренного.
- **До 16 лет профиль закрыт** всем, кроме самого игрока и администраторов его
  клубов, — и посторонний получает 404, а не 403: иначе по адресам страниц
  собирался бы список несовершеннолетних. Скан приказа — только владельцу и
  администраторам, в любом возрасте.
- **Файлы — за интерфейсом `FileStorage`** (сейчас Postgres, `bytea`). Тип
  определяется по сигнатуре байтов, картинки перекодирует `sharp` (EXIF с
  координатами не переживает загрузку), SVG не принимается. Замена — через
  `prune`: у человека остаётся ровно один файл каждого вида.
- **Связь профиля с файлом — `NoAction`, не `Restrict`**: удаление учётки
  уносит профиль и файлы одним оператором, а `Restrict` остановил бы каскад,
  если бы файл удалялся первым.
- **Веб читает файлы байтами** (`useFileUrl`, `api.file`), а не адресом API в
  `<img src>`: картинка по адресу уходит без токена. `Content-Type` в
  `lib/api.ts` ставит `json()`, а не общий запрос — иначе форма с файлом
  теряет границу частей.

### Карточка тренера

Пятый сценарий ТЗ: публичная страница тренера с фото, достижениями,
инвентарём, стоимостью и соцсетями. Правила, которые легко нарушить незаметно:

- **Карточка принадлежит человеку, цены — клубу.** С 20.09.2026 (решение
  владельца, отступление от ТЗ) фотография, достижения, инвентарь и соцсети
  живут в `CoachCard` с ключом `userId` — одна карточка на все клубы, как
  профиль игрока. У пары `(userId, tenantId)` остался `CoachProfile`, и в нём
  только деньги: `groupPrice`, `individualPrice`, `priceNote`. Причина —
  карточка не меняется от того, в каком зале человек сегодня тренирует, а
  прайс меняется.
- **Правит и то и другое только сам тренер.** Администратор карточку и цены
  видит в карточке человека, но не трогает: маршрутов правки чужой карточки
  больше нет вовсе (было в ТЗ, снято тем же решением) — правка из одного клуба
  меняла бы то, что тренер рассказывает о себе соседнему. Отсюда два адреса:
  карточка — `/me/coach-card` (клуба в адресе нет, роль проверяет сервис:
  `RolesGuard` без клуба бессилен), цены — `clubs/:slug/coach/prices` под
  `@Roles('COACH')`.
- **Публичный адрес `/coaches/:id` клуба не несёт** — и теперь не должен:
  карточка платформенная, а клубы перечисляются списком, каждый со своей ценой
  («Тренер в клубах: …»).
- **Фотография — файл, а не адрес.** `photoUrl` в схеме был строкой и не
  использовался; с 18.09.2026 это `photoFileId` со связью на `StoredFile`, вид
  `COACH_PHOTO`, обработка та же, что у аватара. Отдаётся она всем: у карточки
  тренера возрастного ограничения нет, и `canReadFile` отвечает на этот вид
  `true` до всяких проверок.
- **Связь с фото — `NoAction`, как у игрока.** Отложенной (`DEFERRABLE`) она
  была ровно потому, что карточка висела на членстве, на уровень глубже
  учётки, и проверка срабатывала раньше каскада. Теперь `CoachCard` — прямой
  потомок `User` и исчезает в одной волне с файлом; отложенная связь снята
  миграцией `20260920100000_coach_card_platform`.
- **Состав групп собирает `CoachesService`, а не экран смены.** Тренеру не
  положены ни отметки, ни деньги — это работа администратора; зато положены
  полное имя и телефон: ему звонить ученику. Показываются только занятия,
  которые ещё не кончились.
- **Спарринг — та же бронь стола, что у клиента**, с другим владельцем:
  `BookingService.create` принимает `BookingOwner` (`client` или `coach`), и
  второго пути бронирования нет. Отличия ровно три: у тренера не заводится
  `ClientProfile`, ставится `isSparring`, и маршрут лежит в
  `clubs/:slug/coach/sparring` под `@Roles('COACH')`. Ученик в брони не
  записан — `TableBooking` несёт либо клиента, либо тренера.
- **Деньги спарринга считаются не по политике клиента.** Заблаговременная
  отмена тренеру бесплатна (`cancelPercentOf` в `booking.service.ts` отдаёт 0 —
  и в самой отмене, и в обещании «сколько спишется сейчас»), а неявка стоит
  ВСЕЙ аренды: 100 % и у отметки администратора, и у джобы (`noShowRatio` в
  `attendance-rules.ts`, под тестами). Клубные пороги отмены адресованы
  клиенту, и применять их к сотруднику — значит брать с него процент за
  несделанное. Смоуком это не проверить: бронь нельзя начать раньше ближайшего
  шага сетки, а значит, и дождаться её начала в пределах прогона.
- **Спарринг не попадает в «Мои записи».** `EntriesService` собирает записи
  КЛИЕНТА; спарринг — работа сотрудника, и тренер видит его на странице брони.
  Если однажды понадобится в ленте — это отдельное решение, а не недосмотр.
- **Статистика тренера — один расчёт на двоих**: тренер видит её о себе в
  «Моих группах», клуб — в карточке тренера (ТЗ: «статистика посещаемости
  доступна и по каждому тренеру»). Правила — чистая `coachStats` в
  `coaches/coach-stats.ts` под тестами. Главное из них: **посещаемость
  считается только по отмеченным записям**, а неотмеченные показываются
  отдельным числом — иначе смена, где администратор не успел отметить, выглядит
  у тренера днём, когда никто не пришёл. Идущее занятие не считается вовсе.
- **Смоук делает пробные учётки тренерами**, а сценарии расписания берут первого
  тренера клуба — и прогон без уборки перед ним вешает занятия на пробного.
  `clean-probes` поэтому убирает и то, что пробная учётка вела как тренер
  (`removeProbeCoaching`): занятие с пробным тренером — мусор смоука по
  построению.
- **Ссылки на соцсети — только http(s)**, и это правило, а не `@IsUrl`:
  `javascript:` в адресе выполнится у посетителя публичной страницы. Разбор —
  `coach-rules.ts` под тестами, и он же молча отбрасывает негодное, пришедшее
  из базы: `socialLinks` — `Json`, и что там лежит, база не знает.

### Абонементы клиента

Решения владельца от 19.09.2026: продаёт администратор у стойки (онлайн —
вместе с ЮKassa), списание автоматическое при записи, аренда стола пока не
покрывается. Правила, которые легко нарушить незаметно:

- **Истинное состояние визита — сама запись, а не журнал.** `consumed(entry)`
  (`subscriptions/subscription-rules.ts`): записан или пришёл — израсходован;
  отменил или не пришёл — по проценту. У записи по абонементу `chargeRatio` —
  это судьба визита, 0 или 100 (CHECK), а не доля цены.
- **«Сгорел» — это «не вернулся».** Строк `VISIT_BURNED` и `EXPIRED` в журнале
  не бывает вовсе (CHECK): строка «сгорел», записанная при неявке, осталась бы
  ложью навсегда, стоило клубу исправить отметку на «пришёл». Любой переход
  записи сводится к `decideLedger(before, after)` — одно движение или ни одного.
- **Журнал и кэш `remainingVisits` пишет одна функция** — `writeLedger`, под
  `FOR UPDATE` по абонементу. CHECK'ом «кэш равен сумме журнала» не выражается,
  это сравнение таблиц, поэтому правило держит единственный писатель.
- **Порядок блокировок везде один**: строка записи или занятия, потом
  абонемент; подходящие абонементы берутся все сразу по возрастанию `id`.
  Обратный порядок в одном из путей дал бы взаимную блокировку.
- **Запись ссылается на абонемент СВОЕГО клиента** — составной ключ
  `(subscriptionId, clientId, tenantId)`: родитель, записывая ребёнка, не
  заплатит своим абонементом, и это держит база, а не сервис.
- **Срок — до конца местного дня** последнего дня, по поясу **зала продажи**
  (`Subscription.soldAtHallId`): у клуба пояса нет, он свойство зала, и у залов
  в разных регионах день кончается в разное время. Зал продажи у клуба с одним
  залом подставляется молча, с несколькими — обязателен (400). В деньгах дня
  продажа видна тоже только у своего зала: по клубу её показывала бы каждая
  смена. Бессрочный тариф — `durationDays = null`, безлимитный — `visitsCount =
  null`; оба сразу запрещены.
- **Деньги дня запись по абонементу не приносит** (`chargeOf` с `prepaid`):
  они пришли продажей. Сама продажа — отдельной строкой рядом с итогом, не в
  нём, иначе одни деньги посчитались бы дважды.
- **Поздняя отмена по абонементу считается наравне с денежной.** В сводке
  человека её ловит признак `burnedVisit` (`personSummary`), а не сумма:
  денег за ней нет вовсе, и по деньгам человек с абонементом выглядел
  аккуратнее, чем он есть.
- **Журнал абонементов — только вставки**, ровно как журнал аудита: ни UPDATE,
  ни DELETE, без исключений и флагов (прежнюю лазейку для уборки сняло решение
  владельца от 20.09.2026). Цена известна и принята: строку журнала не удалить,
  а значит, не удалить и запись с абонементом, на которые она ссылается
  (Restrict), и учётку клиента за ними. `clean-probes` такие пробные учётки не
  трогает, а называет числом в отчёте (`ledgerLocked`), поэтому смоук ведёт
  абонементы под постоянной учёткой `probe-subscriptions@example.com` и
  постоянным тренером — иначе несносимый остаток рос бы с каждым прогоном.
- **Имена пробных данных смоука — с точными префиксами уборки** («Тариф
  проверки », «Зал проверки »). Имя мимо префикса переживает `clean-probes` и
  остаётся в клубе навсегда.

### Семья: родитель и ребёнок

Расширение сверх ТЗ (решения владельца от 12.09 и 17.09.2026). Пока ребёнку
нет 16, записывает, отменяет и ведёт его профиль родитель; сам ребёнок только
смотрит. Правила, которые легко нарушить незаметно:

- **«За кого» решает `ActingClientGuard`, а не `@Roles('CLIENT')`.** Клиентские
  маршруты записи, отмены, списков и `/me/player` помечены `@ClientAction()`
  (`apps/api/src/guardianship/acting-client.guard.ts`), сервис получает
  `@Acting() acting.userId` вместо `club.userId`. Параметр `?for=<childId>`
  переключает действие на ребёнка. Роль клиента проверяется у того, **за кого**
  действие: родитель-тренер записывает ребёнка как обычный родитель. Новый
  клиентский маршрут с `@Roles('CLIENT')` снова откроет самозапись до 16.
- **Самозаписи до 16 нет.** «За себя» с `mode: 'write'` младше 16 — 403,
  чтение своих записей и профиля — можно. Правила — чистая `decideActing` в
  `guardianship-rules.ts`, под тестами вместе с остальными решениями опеки.
- **Опека кончается по дате, без джобы.** Права = статус `ACTIVE` и ребёнку
  ещё нет 16 на сегодня (`guardianHasRights`); строка остаётся `ACTIVE` и после
  дня рождения. Возраст — только `fullYears` из `@yenisey/types`: две копии
  расчёта (API и карточка человека) уже расходились. В CHECK возраст не выражается — `now()` не IMMUTABLE.
- **Действующее закрепление у ребёнка одно — частичным уникальным индексом**,
  а заявок может быть несколько: уникальность «родитель один» по всем строкам
  дала бы постороннему, знающему почту ребёнка, занять место настоящего
  родителя. Подтверждение одной заявки отклоняет остальные; гонку двух
  подтверждений ловит индекс (P2002 → 409).
- **Ответ на заявку по почте одинаковый при любом исходе**, а исходящие заявки
  родителю не показываются — иначе по форме перебирались бы почты детей.
- **Родителю — только с 18, отзывать может и клуб.** Администратор клуба
  ребёнка снимает закрепление с причиной (CHECK
  `Guardianship_club_revoke_explained`) и строкой аудита: восстановления пароля
  нет, и потерявший учётку родитель иначе навсегда блокирует ребёнка.
- **Смена пароля ребёнку гасит его refresh-сессии** — это первая смена пароля в
  продукте, и другой пока нет.
- **Веб держит выбор в адресе** (`usePersonSwitch`, `?for=`), читая его из
  `window.location` в эффекте — без `useSearchParams` и границ Suspense. Ссылка
  на ту же страницу с другим `?for` её не перемонтирует: переключение внутри
  страницы — через `choose`, не через `<Link>`. Методы `lib/api.ts` принимают
  необязательный `forPerson`, формы профиля берут его из контекста `ForPerson`.

### Окружение

`.env` — один на весь монорепозиторий, в корне, в git не попадает. Переменные валидируются при старте API в `apps/api/src/config/env.ts`, приложение падает сразу. Отдельно проверяется, что `JWT_ACCESS_SECRET` и `JWT_REFRESH_SECRET` различаются: при совпадении refresh-токен принимается как access и обходит короткий срок жизни.

Подробности первого запуска и известные ограничения каркаса — `docs/DEVELOPMENT.md`. Техзадание — `docs/TZ.md`.

## Особенности этой машины (Windows)

- **Claude Code CLI без git-bash не стартует** и сообщает наружу только `exit code 1`. Настоящая ошибка уходит в stderr дочернего процесса, поэтому всё, что запускает CLI программно, должно этот stderr перехватывать — иначе диагностировать нечего. Путь: `X:\Git\bin\bash.exe` (не `System32\bash.exe` — это launcher WSL, и он не подходит).
- **Консоль в cp1251.** `print` с `₽`, эмодзи или длинным тире падает с `UnicodeEncodeError`, а `logging` молча теряет строку — скрипт успевает сделать работу и потерять результат на выводе. В Python-скриптах проекта ставь `PYTHONIOENCODING=utf-8` или перенастраивай `sys.stdout` первой строкой, а всем `basicConfig` задавай `encoding="utf-8"`.
- **`core.autocrlf=true`.** Контрольные суммы вендоренных скиллов в `.claude/skills/` считаются по LF-байтам, поэтому в `.gitattributes` для них стоит `text eol=lf`. Без этого свежий чекаут даёт «stale snapshot» и скилл молча не грузится.
- **TLS нестабилен.** `git push` периодически падает с `schannel: failed to receive handshake` — повторить. Проверяй код возврата именно `git`: `git push | tail -3` всегда вернёт 0.
- **MCP-серверу нельзя давать `@latest`.** `npx -y chrome-devtools-mcp@latest` каждый запуск идёт в реестр npm и на этой машине стартует 39 секунд — при таймауте подключения MCP в 30 секунд сервер не поднимается никогда, а наружу видно только `CONNECT_TIMEOUT`. Пакет стоит глобально (`npm i -g chrome-devtools-mcp`), а в `.mcp.json` команда без версии: старт 1,4 секунды. Так же стоит поступать с любым новым stdio-сервером.
- Образы с Docker Hub не тянутся (TLS-таймаут), Postgres установлен нативно.
